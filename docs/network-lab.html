Who can access what? planned · not tested

These are the rules we plan to set on the firewall. They still need to be configured and tested.

  • Windows can: access shared files on TrueNAS (SMB, port 445) and view the Grafana monitoring dashboard.
  • The administrator on PC A can: manage the firewall and TrueNAS, connect to Ubuntu using an SSH key, and access Grafana (port 3001).
  • Monitoring can: collect Windows metrics on port 9182. OPNsense can send its logs to Ubuntu on port 514.
  • Blocked: direct access from the internet to internal services. VPN users cannot access TrueNAS shared files, Ubuntu SSH or Grafana under the current proposal.
  • Not decided yet: access to the future application, its ports, permissions, storage and backup.

Any other new connection is intended to be blocked and recorded in the firewall logs.

Application: to be decided

Docker hosts a future application on Ubuntu. Its identity, ports, permissions, data storage and backup are not confirmed. Prometheus stays local on 127.0.0.1:9090; Grafana is planned on 3001.

VM escape: security demonstration

Risk: a flaw in the hypervisor or a guest integration feature could let an attacker leave one VM and reach the host or another VM.

Show the protections: check the VMware version and security updates; disable unused shared folders, clipboard, drag-and-drop and unnecessary devices; show that only authorized VM network connections succeed and collect firewall or system logs.

These checks demonstrate risk reduction. They do not prove that a VM escape is impossible. Planned, not tested.

Other virtualization risks

Misconfigured virtual networks can expose a VM; compromised accounts can access services; unprotected snapshots or VM files can leak data; excessive resource use can slow or stop other VMs.

Reduce these risks with restricted network rules, limited accounts, protected VM files and backups, updates, and resource monitoring.

Configuration documentation

Document each step with actual settings and evidence:

  1. Describe the virtualization security risks and the network diagram.
  2. Record VM, firewall, VLAN and VPN configuration.
  3. Document TrueNAS storage and the chosen containerized application.
  4. Record the VM-escape protection checks and authorized/blocked access tests, with real results and screenshots.

Keep unfinished steps clearly marked as pending.

Storage protection

Test SMB users and ACLs, encrypted dataset, snapshots and file restore. Two virtual data disks on the same physical SSD do not constitute independent physical backup.

Capacity and uncertainties

PC B: 15.29 GiB usable RAM. Test allocations: Ubuntu Desktop 4 GiB, TrueNAS 6 GiB and Alpine 0.5 GiB, or 10.5 GiB total. TrueNAS 6 GiB is below its documented 8 GiB VM minimum; Ubuntu Desktop 4 GiB is below the 6 GB recommended for a comfortable experience. Startup and simultaneous performance remain untested. Tagged Ethernet transport is unverified.

Why Alpine?

SW-B maps the tagged Ethernet trunk to separate untagged Ubuntu and NAS access networks. It is an implementation choice, not a course requirement. Direct guest VLAN tagging may remove it, but compatibility and isolation are unverified; the baseline retains Alpine pending a tested alternative.

First joint check

Test VLAN 20/30 transport across both Ethernet adapters early. Capture the outcome and stop deeper configuration if tags do not pass. Also check host memory under the intended simultaneous load.
